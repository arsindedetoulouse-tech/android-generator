# android-project-generator Specification

## Purpose

Генерировать чистые модульные Android-проекты и добавлять в них фичи по единым соглашениям, не перенося предметную логику AppScanner.

## Requirements

### Requirement: Создание чистого Android-проекта
CLI SHALL создавать модульный Android-проект в текущем пустом каталоге, используя согласованный стек, навигацию Navigation 3 и SDK baseline без AppScanner-специфичных функций и бизнес-правил.

#### Scenario: Создание проекта с валидными параметрами
- **WHEN** пользователь запускает `android-skeleton create` в пустом каталоге с валидными `--package` и `--application-id`
- **THEN** CLI создаёт `app`, `app:navigation`, `build-logic`, version catalog, модуль навигации `:core:navigation`, модуль хранения `:core:datastore`, общие слои `:common:domain`, `:common:data`, `:common:presentation`, модуль тестов `:common:testing`, модуль фичи `:feature:home`, API-модуль фичи `:feature:home-api` и design system

#### Scenario: Навигация сгенерированного проекта
- **WHEN** CLI создаёт проект
- **THEN** навигация построена на Navigation 3, а маршруты объявлены как сериализуемые типизированные ключи, а не как строковые константы

#### Scenario: Отсутствие пустых слоёвых модулей
- **WHEN** CLI создаёт проект
- **THEN** слои `domain` и `data` каждой фичи размещаются в общих модулях `:common:domain` и `:common:data`, которые не пусты, а feature-модуль содержит только `presentation`, DI-регистрации и заглушку данных

#### Scenario: Оформление и тема приложения
- **WHEN** CLI создаёт проект
- **THEN** design system предоставляет токены, типографику, палитру и тёмную тему, а манифест задаёт тему, совместимую с Compose и edge-to-edge

#### Scenario: Порядок модулей в конфигурации сборки
- **WHEN** CLI создаёт проект
- **THEN** список подключаемых модулей содержит все `common`- и `core`-модули раньше feature-модулей, а файл не содержит пустых строк внутри списка

#### Scenario: Каталог назначения не пуст
- **WHEN** пользователь запускает `create` в каталоге с файлами или подкаталогами
- **THEN** CLI сообщает о конфликте и не изменяет каталог

#### Scenario: Имя проекта не задано
- **WHEN** пользователь не передаёт `--name`
- **THEN** root project name и label приложения выводятся из имени текущего каталога

#### Scenario: Валидация package и application ID
- **WHEN** один из обязательных идентификаторов имеет неверный формат
- **THEN** CLI сообщает об ошибке до создания файлов

### Requirement: Настройка дополнительных модулей и локалей
CLI SHALL включать модуль хранения `:core:datastore` в каждый создаваемый проект, модуль сети `:core:network` только по явному запросу и SHALL настраивать выбранные BCP-47 локали для Android resources и per-app language settings.

#### Scenario: Выбрана опциональная инфраструктура
- **WHEN** пользователь передаёт `--network`
- **THEN** CLI создаёт нейтральный модуль `:core:network` и подключает его в Gradle, dependency injection и разрешения приложения

#### Scenario: Опциональная инфраструктура не выбрана
- **WHEN** пользователь не передаёт `--network`
- **THEN** модуль `:core:network` и его зависимости отсутствуют, а разрешение доступа в Интернет не запрашивается

#### Scenario: Модуль хранения присутствует без флагов
- **WHEN** пользователь запускает `create` без флагов инфраструктуры
- **THEN** CLI создаёт `:core:datastore`, подключает его в Gradle и регистрирует его модуль в composition root

#### Scenario: Публичные типы хранения доступны потребителям
- **WHEN** модуль фичи обращается к типам хранилища из общего модуля слоя `data`
- **THEN** типы хранилища объявлены как часть публичного контракта модуля `:core:datastore` и видны потребителям без дополнительных зависимостей

#### Scenario: Выбраны валидные локали
- **WHEN** пользователь передаёт один или несколько валидных BCP-47 тегов через повторяемый `--locale`
- **THEN** CLI создаёт соответствующие Android resources и locale configuration

#### Scenario: Передана невалидная локаль
- **WHEN** хотя бы один переданный locale tag невалиден
- **THEN** CLI сообщает об ошибке и не создаёт файлы проекта

#### Scenario: Флаг хранения отклонён
- **WHEN** пользователь передаёт `--datastore`
- **THEN** CLI отклоняет запуск как неизвестный параметр, потому что модуль хранения входит в состав каждого проекта

### Requirement: Добавление feature-модуля
Команда `add-feature` SHALL добавлять рабочий Gradle feature-модуль со слоем `presentation`, DI-регистрациями и заглушкой данных, добавляя слои `domain` и `data` этой фичи в общие модули, и SHALL создавать отдельный API-модуль только с навигационным контрактом.

#### Scenario: Добавление фичи в поддерживаемый проект
- **WHEN** пользователь запускает `android-skeleton add-feature <name>` с валидным kebab-case slug в проекте с поддерживаемой metadata
- **THEN** CLI создаёт компилируемый feature skeleton, обновляет Gradle и DI-регистрации и предоставляет route contract для интеграции навигации

#### Scenario: Пакет и идентификаторы фичи
- **WHEN** пользователь добавляет фичу с именем `user-profile`
- **THEN** CLI создаёт lowercase Kotlin package `feature.userprofile` в feature-модуле и `domain.userprofile`, `data.userprofile` в общих слоях, а типы с именами в PascalCase

#### Scenario: Навигационный контракт API-модуля
- **WHEN** CLI создаёт API-модуль фичи
- **THEN** API-модуль является Android-модулем, а его маршрут объявлен как сериализуемый типизированный ключ, пригодный для сохранения back stack

#### Scenario: Рабочая цепочка feature-модуля
- **WHEN** CLI добавляет фичу
- **THEN** CLI создаёт реализацию источника данных и реализацию репозитория в общем слое `data`, модель, интерфейс репозитория и use case в общем слое `domain`, интенты во ViewModel, вызывающие use case, регистрирует источник данных, репозиторий и use case в DI, а состояние отражает загрузку, данные и ошибку

#### Scenario: Одноимённые типы разных фич не сталкиваются
- **WHEN** CLI добавляет две фичи с одинаковым именем типа в домене
- **THEN** типы каждой фичи объявлены в собственном пакете общего слоя и потому не конфликтуют

#### Scenario: Вкладка навигации фичи
- **WHEN** CLI добавляет фичу
- **THEN** CLI создаёт вкладку навигации фичи, добавляющую её маршрут в граф приложения, и сообщает готовый фрагмент кода для подключения вкладки

#### Scenario: Имена ресурсов фичи включают её слаг
- **WHEN** CLI создаёт две фичи
- **THEN** строковые ресурсы каждой получают имена с префиксом из её слага, чтобы при слиянии ресурсов одноимённые строки разных фич не перекрывали друг друга

#### Scenario: Зарезервированное имя фичи
- **WHEN** пользователь добавляет фичу с именем `home`
- **THEN** CLI отклоняет запрос с сообщением о том, что это имя зарезервировано под начальный экран приложения, и не изменяет проект

#### Scenario: NavHost остаётся ответственностью приложения
- **WHEN** CLI добавляет фичу
- **THEN** CLI не изменяет исходники приложения и сообщает, что destination требуется зарегистрировать вручную

#### Scenario: Проект не поддерживается
- **WHEN** metadata отсутствует, неизвестна или несовместима с версией шаблона
- **THEN** CLI сообщает, что проект не поддерживается, и не изменяет его

### Requirement: Покрытие feature-модуля тестами
CLI SHALL создавать для каждой добавленной фичи юнит-тесты ViewModel и репозитория рядом с проверяемым кодом, используя подставные зависимости без Android-окружения.

#### Scenario: Тесты добавленной фичи
- **WHEN** CLI добавляет фичу
- **THEN** CLI создаёт тест репозитория в общем слое `data` рядом с его реализацией и тест ViewModel в feature-модуле, оба на подставных зависимостях

#### Scenario: Проверка состояний загрузки
- **WHEN** тест ViewModel выполняется
- **THEN** тест проверяет переход состояния в загрузку и в состояние с данными либо с ошибкой

#### Scenario: Проверка офлайн-цепочки
- **WHEN** тест репозитория выполняется
- **THEN** тест проверяет, что репозиторий возвращает удалённые данные, отдаёт кэш при отказе и пробрасывает ошибку при отсутствии кэша

### Requirement: Начальный экран приложения
CLI SHALL оформлять начальный экран как самостоятельную фичу с собственным маршрутом, вкладкой навигации и ресурсами, а не как содержимое модуля навигации.

#### Scenario: Начальный экран подключён как фича
- **WHEN** CLI создаёт проект
- **THEN** начальный экран объявлен как сериализуемый ключ в API-модуле фичи, отрисовывается вкладкой навигации среди прочих установщиков и не регистрируется вручную в composition root

#### Scenario: Состав начального экрана
- **WHEN** CLI создаёт проект
- **THEN** начальный экран использует ту же цепочку, что и любая другая фича, включая реализацию источника данных, реализацию репозитория и use case в общих слоях, ViewModel и DI-регистрации в feature-модуле

#### Scenario: Граф навигации не содержит app-owned destination
- **WHEN** CLI создаёт проект
- **THEN** модуль навигации отвечает только за сборку графа и не содержит экранов

### Requirement: Оформление начального экрана
CLI SHALL отрисовывать на начальном экране приветствие по центру и SHALL показывать данные заглушки сразу, не отображая состояние отсутствия данных.

#### Scenario: Приветствие по центру экрана
- **WHEN** приложение запущено
- **THEN** начальный экран показывает приветствие по центру экрана

#### Scenario: Первый запуск с заглушкой источника данных
- **WHEN** приложение запущено, а реальный источник данных ещё не подключён
- **THEN** начальный экран показывает приветствие и значение из заглушки, без сообщения об отсутствии данных

#### Scenario: Данные после замены источника
- **WHEN** источник данных начального экрана возвращает модель
- **THEN** начальный экран показывает приветствие и значение модели под ним

#### Scenario: Ошибка загрузки видна пользователю
- **WHEN** загрузка начального экрана завершается ошибкой
- **THEN** начальный экран показывает приветствие и текст ошибки под ним

### Requirement: Опциональный возврат в экране фичи
CLI SHALL создавать экран фичи с необязательным действием возврата: кнопка возврата SHALL отображаться только когда действие передано.

#### Scenario: Экран без действия возврата
- **WHEN** экран фичи создан без действия возврата
- **THEN** кнопка возврата не отображается

#### Scenario: Экран с действием возврата
- **WHEN** экран фичи создан с действием возврата
- **THEN** кнопка возврата отображается и вызывает переданное действие

#### Scenario: Начальный экран без мёртвой кнопки
- **WHEN** приложение запущено
- **THEN** начальный экран не содержит кнопки возврата, которая не может выполнить переход

### Requirement: Использование версионированного локального шаблона
CLI SHALL поставлять Android-шаблон в установленном пакете, записывать его точную версию в metadata проекта и проверять совместимость шаблона перед генерацией и добавлением фичи.

#### Scenario: Создание проекта без сетевого доступа
- **WHEN** пользователь запускает `create` с установленным CLI-пакетом
- **THEN** CLI использует локально поставляемый шаблон без загрузки файлов из сети

#### Scenario: Фиксация версии шаблона
- **WHEN** CLI создаёт проект
- **THEN** он сохраняет версии CLI и шаблона в metadata проекта

#### Scenario: Несовместимая версия шаблона
- **WHEN** версия шаблона проекта не поддерживается установленным CLI
- **THEN** CLI сообщает об этом до записи файлов и не изменяет проект

#### Scenario: Версия для add-feature
- **WHEN** `add-feature` запускается в сгенерированном проекте
- **THEN** CLI выбирает совместимые шаблонные файлы по версии, записанной в metadata проекта

#### Scenario: Проект предыдущей версии шаблона
- **WHEN** `add-feature` запускается в проекте, созданном шаблоном предыдущей версии
- **THEN** CLI отказывается работать с этим проектом, называя версию установленного CLI, версию шаблона проекта и способ обойти отказ

#### Scenario: Обход отказа по версии
- **WHEN** пользователь явно требует продолжить работу с проектом чужого шаблона
- **THEN** CLI выполняет команду, а решение остаётся за пользователем

### Requirement: Безопасное применение изменений к проекту
CLI SHALL валидировать полный план изменений до записи и SHALL предотвращать частично применённые изменения при обработанной ошибке записи.

#### Scenario: Предварительный просмотр
- **WHEN** пользователь передаёт `--dry-run` для `add-feature`
- **THEN** CLI показывает план файлов и интеграций без изменения проекта

#### Scenario: Конфликт целевого пути или регистрации
- **WHEN** любой целевой путь или регистрация фичи уже существует
- **THEN** CLI сообщает о конфликте до записи и не перезаписывает существующие данные

#### Scenario: Ошибка применения плана
- **WHEN** применение плана завершается ошибкой после изменения одного или нескольких файлов
- **THEN** CLI восстанавливает изменённые файлы и сообщает об ошибке

#### Scenario: Небезопасный путь шаблонного файла
- **WHEN** путь рендеримого файла выходит за пределы каталога проекта
- **THEN** CLI отклоняет план и не записывает файлы

### Requirement: Проверяемая компилируемость сгенерированного проекта
CLI SHALL предоставлять opt-in проверку сборки для обеих команд, SHALL создавать сгенерированный код так, чтобы его тесты фактически выполнялись, и SHALL проверять наличие Android SDK до запуска сборки.

#### Scenario: Проверка добавленной фичи
- **WHEN** пользователь запускает `add-feature` с флагом проверки сборки
- **THEN** CLI после записи файлов запускает сборку проекта и сообщает о результате

#### Scenario: Ошибка проверки сборки
- **WHEN** сборка проекта завершается ошибкой после проверки
- **THEN** CLI сообщает об ошибке и сохраняет сгенерированный проект

#### Scenario: Проверка не запрошена
- **WHEN** пользователь не передаёт флаг проверки сборки
- **THEN** CLI не запускает сборку и завершает работу сразу после записи файлов

#### Scenario: Тесты сгенерированной фичи выполняются
- **WHEN** пользователь запускает задачу тестов в сгенерированном feature-модуле
- **THEN** тесты ViewModel и репозитория выполняются, а не только компилируются

#### Scenario: Расположение SDK проверяется до сборки
- **WHEN** пользователь запускает проверку сборки, а местоположение Android SDK не определено ни через переменные окружения, ни через файл настроек проекта
- **THEN** CLI не запускает сборку и сообщает, какие источники проверены, какие варианты найдены на машине и как задать расположение SDK

#### Scenario: Заданное расположение SDK проверяется на пригодность
- **WHEN** расположение Android SDK определено, но указанный каталог не содержит признаков SDK
- **THEN** CLI сообщает об этом до запуска сборки вместо того, чтобы передать отказ Gradle

#### Scenario: Требуемая платформа отсутствует в SDK
- **WHEN** расположение Android SDK определено, но в нём нет платформы, требуемой объявленным в проекте уровнем компиляции
- **THEN** CLI сообщает требуемый и установленные уровни до запуска сборки

#### Scenario: Расположение SDK задано явно
- **WHEN** пользователь передаёт расположение Android SDK как параметр команды
- **THEN** CLI записывает его в файл настроек проекта и выполняет проверку сборки с этим расположением

#### Scenario: Переданное расположение SDK непригодно
- **WHEN** переданное как параметр расположение Android SDK не существует или не содержит признаков SDK
- **THEN** CLI сообщает об ошибке и не записывает расположение в файл настроек

#### Scenario: SDK не настроен, проверка не запрошена
- **WHEN** пользователь не передаёт флаг проверки сборки, а местоположение Android SDK не определено
- **THEN** CLI завершает генерацию успешно и предупреждает о ненастроенном SDK со ссылкой на справку

### Requirement: Офлайн-цепочка данных фичи
CLI SHALL создавать источник данных фичи с раздельным чтением локального кэша, загрузкой удалённых данных и сохранением в кэш, а репозиторий SHALL отдавать кэш при отказе загрузки.

#### Scenario: Успешная загрузка сохраняет кэш
- **WHEN** удалённая загрузка фичи возвращает модель
- **THEN** репозиторий возвращает модель и сохраняет её в локальный кэш для последующих запусков

#### Scenario: Отказ загрузки отдаёт кэш
- **WHEN** удалённая загрузка фичи завершается ошибкой, а локальный кэш содержит модель
- **THEN** репозиторий возвращает модель из кэша и не сообщает об ошибке

#### Scenario: Отказ загрузки без кэша
- **WHEN** удалённая загрузка фичи завершается ошибкой, а локальный кэш пуст
- **THEN** репозиторий пробрасывает ошибку вызывающему коду

#### Scenario: Отмена загрузки не превращается в ошибку данных
- **WHEN** загрузка фичи отменена во время выполнения
- **THEN** состояние остаётся без ошибки данных и отмена не перехватывается как сбой

### Requirement: Типизированная ошибка в состоянии фичи
CLI SHALL выражать ошибку в состоянии фичи типизированным значением из закрытого множества, а не строкой с текстом исключения.

#### Scenario: Ошибка сети распознаётся
- **WHEN** загрузка фичи завершается ошибкой ввода-вывода
- **THEN** состояние содержит значение ошибки сети, а не текст исключения

#### Scenario: Прочие сбои не выдаются за сеть
- **WHEN** загрузка фичи завершается ошибкой, отличной от ошибки ввода-вывода
- **THEN** состояние содержит значение неизвестной ошибки

#### Scenario: Успешная загрузка очищает ошибку
- **WHEN** загрузка фичи завершается успешно после предыдущей ошибки
- **THEN** состояние не содержит ошибки

### Requirement: Заглушка данных фичи
CLI SHALL поставлять заглушку данных каждой фичи, чтобы приложение показывало содержимое до подключения реального бэкенда, и SHALL извлекать из неё идентификатор независимо от формы ответа.

#### Scenario: Приложение запускается без бэкенда
- **WHEN** приложение запущено, а реальный источник данных не подключён
- **THEN** фича показывает идентификатор, извлечённый из заглушки

#### Scenario: Форма ответа не задана заранее
- **WHEN** заглушка содержит произвольный валидный JSON без известного идентификатора на верхнем уровне
- **THEN** фича сохраняет полный ответ как идентификатор и не отбрасывает данные

#### Scenario: Идентификатор есть во вложенном объекте
- **WHEN** заглушка содержит вложенный объект с идентификатором
- **THEN** фича использует идентификатор вложенного объекта

### Requirement: Релизная сборка приложения
CLI SHALL создавать конфигурацию release с минификацией кода и сжатием ресурсов и SHALL поставлять правила ProGuard для неё.

#### Scenario: Release-сборка уменьшает объём
- **WHEN** собирается release-вариант приложения
- **THEN** минификация кода и сжатие ресурсов включены, а правила ProGuard поставляются вместе с модулем приложения

### Requirement: Универсальный HTTP-клиент
CLI SHALL создавать нейтральный HTTP-клиент без привязки к адресам сервисов, с явными таймаутами и без автоматического подъёма исключений на неуспешный ответ.

#### Scenario: Неуспешный ответ доходит до вызывающего кода
- **WHEN** сервер отвечает статусом ошибки
- **THEN** клиент не выбрасывает исключение автоматически, а передаёт ответ вызывающему коду

#### Scenario: Запрос не зависает бесконечно
- **WHEN** клиент выполняет запрос
- **THEN** для запроса, подключения и сокета заданы явные таймауты

### Requirement: Диагностика окружения Android SDK
CLI SHALL определять кандидатов на местоположение Android SDK для инструкции пользователю и SHALL считать каталог SDK только по признакам SDK, а не по факту существования.

#### Scenario: Частично настроенная машина
- **WHEN** утилиты SDK доступны через `PATH`, но переменные, которые читает сборка, не заданы
- **THEN** CLI выводит в инструкции расположение SDK, восстановленное из положения утилит, и не считает машину настроенной

#### Scenario: Каталог не является SDK
- **WHEN** каталог существует, но не содержит ни платформ, ни утилит SDK
- **THEN** CLI не предлагает его как расположение SDK

#### Scenario: Инструкция не зависит от оболочки
- **WHEN** CLI формирует инструкцию по настройке SDK
- **THEN** инструкция содержит шаги для zsh, bash и fish, а также для Windows, и не полагается на определение текущей оболочки

#### Scenario: SDK не установлен
- **WHEN** на машине не найдено ни одного кандидата на местоположение SDK
- **THEN** инструкция предлагает установить утилиты командной строки без Android Studio и содержит ссылку на их загрузку

### Requirement: Проверка актуальности установленного генератора
CLI SHALL проверять актуальность установленного CLI до генерации и SHALL сообщать результат, не блокируя создание проекта.

#### Scenario: Версия генератора объявлена
- **WHEN** CLI начинает создание проекта
- **THEN** CLI сообщает версию установленного CLI и версию его шаблона до генерации файлов

#### Scenario: Доступна более новая опубликованная версия
- **WHEN** последняя опубликованная версия генератора новее установленной
- **THEN** CLI предупреждает об этом, называет установленную и доступную версии и указывает команду обновления, после чего продолжает генерацию

#### Scenario: Генератор ниже требуемой версии
- **WHEN** версия шаблона, заявленная установленным CLI, требует более новой версии самого CLI
- **THEN** CLI сообщает об этом до генерации, чтобы пользователь не создал проект пакетом, который его не обслуживает

#### Scenario: Константы пакета не согласованы
- **WHEN** версия шаблона в коде, версия шаблона в манифесте и требуемая версия CLI в карте поддерживаемых версий не совпадают
- **THEN** CLI предупреждает о расхождении, указывая значения, и продолжает генерацию

#### Scenario: Пакет установлен из исходников
- **WHEN** пакет установлен из рабочего дерева, а версия в его исходниках новее версии, записанной при установке
- **THEN** CLI предупреждает, что рабочее дерево впереди установленной копии, и называет обе версии

#### Scenario: Обычная копия пакета
- **WHEN** пакет установлен как копия файлов, а не из исходников
- **THEN** CLI не выполняет сверку с исходниками, потому что рабочее дерево ему недоступно

#### Scenario: Ничего не опубликовано
- **WHEN** у генератора нет опубликованных релизов или пакет не опубликован в индексе пакетов
- **THEN** CLI сообщает об отсутствии публикации как о факте и не считает это расхождением версий

#### Scenario: Сеть недоступна
- **WHEN** проверка по внешним источникам не удалась из-за недоступности сети
- **THEN** CLI сообщает, что подтвердить актуальность не удалось, и продолжает генерацию

#### Scenario: Проверка не блокирует генерацию
- **WHEN** обнаружено расхождение версий, отличное от расхождения с шаблоном проекта
- **THEN** CLI создаёт проект и лишь сообщает о расхождении
