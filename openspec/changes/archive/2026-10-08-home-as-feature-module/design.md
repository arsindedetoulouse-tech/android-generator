# Design

## Context

Состояние после перехода шаблона на Navigation 3 (см. архив `2026-10-08-android-template-1-1-0`). Начальный экран — единственный destination, который не проходит по правилам, зафиксированным для остальных:

```
:app:navigation
  AppRoutes.kt       HomeRoute : AppRoute, START_ROUTE, TOP_LEVEL_ROUTES
  AppEntryProvider   typealias + сборка графа, внутри entry<HomeRoute> { HomeScreen() }
  HomeScreen.kt      единственный экран без состояния, без вкладки, без ресурсов фичи
  strings.xml        home_title, home_empty_graph_hint
```

Фича, добавленная через `add-feature`, устроена иначе: маршрут живёт в отдельном API-модуле, экран принадлежит feature-модулю, подключение происходит вкладкой, ресурсы — в модуле фичи. Разница видна только в структуре, и именно она держит слои раздельно.

Два дефекта вывода конфигурации, оба воспроизводятся в эталонном проекте:

```
settings.gradle.kts                       settings.gradle.kts (сейчас)
    ":core:designsystem",                     ":core:designsystem",
    ":core:navigation",          <- якорь ->    ":feature:user-profile",      <- вставлено сюда
                                             __OPTIONAL_MODULE_INCLUDES__
__OPTIONAL_MODULE_INCLUDES__              (схлопывается в "")
)
(пустая строка перед `)`)
```

Причина первого — якорь вставки feature-модулей задан строкой `":core:designsystem",`, которая перестала быть последней строкой списка после появления `:core:navigation`. Причина второго — плейсхолдер опциональных include занимает отдельную строку и при пустом наборе оставляет её после себя.

Один вывод поведения, важный для выбора решения по экрану: `NavigationEventHandler` в Nav3 включает свой back-handler только когда у текущей сцены есть предыдущие записи.

```kotlin
isBackEnabled = sceneState.currentScene.previousEntries.isNotEmpty()
```

Поэтому системный жест на стартовом маршруте не перехватывается и доходит до Activity — приложение закрывается штатно. Обработчик `goBack()` с no-op на старте недостижим из жеста, и выход из приложения не сломан.

## Goals / Non-Goals

**Goals:**

- Убрать из состава модулей единственное исключение из правил, зафиксированных для фич.
- Зафиксировать поведение первого запуска: что пользователь видит до замены источника данных.
- Устранить кнопку, которая на стартовом экране не может выполнить переход.
- Убрать пустую строку и вернуть предсказуемый порядок модулей в `settings.gradle.kts`.

**Non-Goals:**

- Облегчение или сокращение цепочки home: она остаётся полной и выглядит как любая другая фича.
- Миграция уже созданных проектов на новый порядок модулей.
- Изменение поведения экранов существующих фич: у них действие возврата передаётся, значит кнопка остаётся.
- Перенос `MainActivity` из `:app` в `:app:navigation`.
- Перенос приветствия в строки модуля `:app`: весь контент уезжает в модуль фичи.

## Decisions

### Начальный экран становится фичей, порождаемой `create`

`create` создаёт `:feature:home` и `:feature:home-api`, а `:app:navigation` остаётся только сборкой графа.

Альтернатива: оставить Home в `:app:navigation`. Отклонена — она и была причиной: модуль одновременно отвечает за граф и за контент, а вкладка `entry<HomeRoute>` живёт вручную в composition root, тогда как все остальные destinations приходят установщиками.

Альтернатива: отдельный `:app:home` по аналогии с `:app:navigation`. Отклонена — Home остался бы «частью приложения», то есть сохранилось бы то же исключение, только в другом модуле.

Рендеринг переиспользует `_render_feature_templates` с идентичностью `home`: тот же набор шаблонных файлов, что и у `add-feature`, поэтому новый код генерации фич не дублируется. Метаданные проекта получают `features: ["home"]`, поэтому список остаётся правдивым и `add-feature home` отказал бы даже без отдельной проверки.

### `onBack` в общем шаблоне экрана становится необязательным

Кнопка возврата рисуется только когда действие передано; Home передаёт `null`.

Альтернатива: убрать кнопку возврата из общего шаблона и оставить только системный жест. Отклонена — у фичи, открытой поверх другой, возврат нужен и без кнопки её негде вызвать; решение лишает каждую фичу легитимного способа вернуться.

Альтернатива: отдельный шаблон экрана для Home. Отклонена — ради одной отсутствующей кнопки пришлось бы расщепить шаблон, который сейчас единый; необязательный параметр выражает то же самое и не трогает чужие экраны.

### Экран Home отдельный: приветствие по центру, без состояния «ничего не показать»

Приветствие приходит из строковых ресурсов, а не из данных. Под ним отрисовываются загрузка, ошибка и данные; ветка «ничего не показать» отсутствует.

Альтернатива: отцентрировать общий шаблон экрана и брать приветствие из `model.id` заглушки. Отклонена — компоновка изменилась бы у каждого сгенерированного экрана, включая push-экраны, где контент обычно прижат к верху, и приветствие зависело бы от того, что вернёт заглушка.

Альтернатива: параметр выравнивания в общем шаблоне. Отклонена — в публичном API каждого экрана появляется параметр ради одного случая, который дешевле выразить отдельной функцией отрисовки.

Следствие, принятое осознанно: первый запуск показывает только приветствие, потому что заглушка возвращает `null`. Цепочка при этом живая — реализации существуют, зарегистрированы в DI и вызываются, — и покрыта сгенерированными тестами. Сообщение «ничего не показать» убрано, потому что именно его вы просили не видеть.

### Порядок include задаётся последней строкой списка

Якорь вставки в `settings.gradle.kts` переносится на `":feature:home-api",`, а список в шаблоне выстраивается как `app`, `common`, `core`, затем фичи. Новые фичи попадают в конец списка.

Альтернатива: оставить якорь на `":core:designsystem",`. Отклонена — это и есть причина: строка перестала быть последней, и добавляемые модули оказывались перед `:core:navigation`.

### Пустая строка устраняется переносом плейсхолдера

Плейсхолдер опциональных include переносится на строку последнего модуля, а подстановка начинается с перевода строки, когда есть хотя бы один модуль.

```
без опций            с двумя опциями
":feature:home-api",     ":feature:home-api",
)                        ":core:network",
                         ":core:datastore",
                         )
```

Альтернатива: удалять пустые строки постфактум в `project.py`. Отклонена — правило «убрать строку, которая стала пустой после подстановки» пришлось бы применять ко всем шаблонам и рисковать тем, что осмысленная пустая строка исчезнет; локальная правка в одном шаблоне предсказуемее.

### Зарезервированный слаг отклоняется явно

`add-feature home` отклоняется до записи файлов с сообщением о том, что имя зарезервировано под начальный экран. Проверка стоит рядом с проверкой формата слага.

Альтернатива: полагаться на совпадение по metadata. Отклонена — отказ случился бы, но сообщение «уже зарегистрировано» не объясняет, что `home` нельзя использовать в принципе, и провоцирует подбор похожего имени вместо понимания причины.

## Risks / Trade-offs

- **Ручная правка `settings.gradle.kts` в существующем проекте приведёт к отказу `add-feature`** → якорь остаётся проверяемым на единственное вхождение, отказ сообщает о несовместимости формата файла. Такой проект и раньше получал отказ при изменении отступов или хвостовых запятых; риск не новый.
- **Полная цепочка home выглядит избыточной для экрана-приветствия** → это осознанный размен в пользу единообразия: разработчик видит полный путь от источника данных до экрана на старте проекта. Облегчённый скелет отклонён сознательно, чтобы правила для фич не имели исключения.
- **Приветствие не исчезнет после загрузки данных** → приветствие остаётся, значение модели появляется под ним. Если это нежелательно, экран Home правится вручную; это обычная правка приложения, а не шаблона.
- **Начальный экран не показывает данные до замены заглушки** → описано в спецификации отдельным требованием, чтобы это было ожидаемым поведением, а не сюрпризом.
- **Эталонный проект придётся пересобрать** → он перестаёт соответствовать шаблону; пересборка входит в задачи и проверяется на устройстве.
