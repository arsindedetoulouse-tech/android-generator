# Design

## Context

Проверка актуальности нужна из-за расхождения, обнаруженного на практике: копия `0.2.0` от 8 октября в окружении, `0.3.0` в рабочем дереве. `create` отрабатывала молча, и расхождение всплыло только при сборке проекта.

Ограничения, определившие решение:

- **Внешних эталонов пока нет.** `pypi.org/pypi/android-skeleton/json` отдаёт 404, релизов и тегов на GitHub нет. Сравнивать с ними нечего до первой публикации, и проверка обязана отличать «ничего не опубликовано» от «опубликована более старая версия».
- **Обычная копия пакета не знает о рабочем дереве.** В окружении pipx каталог шаблона — физические файлы, `.git` рядом отсутствует. Сверка с исходниками возможна только при редактируемой установке, где окружение содержит путь к репозиторию.
- **Расхождений два.** CLI отстал от внешнего эталона, и CLI не совпадает с шаблоном проекта, в котором работает. Второе ловится в проекте, первое — снаружи.
- **Проверка обязана быть дешёвой и необязательной.** `create` идёт в пустой каталог и может вызываться из скрипта, поэтому блокировать работу она может только в одном случае.

Мотивация — в `proposal.md`, наблюдаемое поведение — в `specs/android-project-generator/spec.md`.

## Goals / Non-Goals

**Goals:**
- Пользователь видит версию генератора до генерации и узнаёт о расхождении сразу.
- Проверка не ломает офлайн-работу и скрипты.
- Расхождение с шаблоном проекта даёт отказ с объяснением, а не безликую ошибку.

**Non-Goals:**
- Автоматическое обновление генератора: CLI не управляет pip и pipx, self-update у pipx не существует.
- Публикация пакета и создание первого релиза — это отдельная работа по подготовке поставки.
- Сравнение с `HEAD` локального репозитория: у копии пакета репозитория нет, а у пользователей тем более.

## Decisions

### 1. Пять независимых проверок вместо одной

**Выбор.** Внутренняя согласованность пакета, сверка с исходниками при редактируемой установке, релиз на GitHub, версия на индексе пакетов, версия шаблона проекта — каждая отдельная функция, возвращающая собственный результат или «проверить не удалось».

**Почему.** Они отвечают на разные вопросы и могут отказать по разным причинам. Объединённая проверка «актуальна ли версия» смешала бы рассинхрон констант сборки с отставанием от публикации, и сообщение перестало бы объяснять, что делать.

### 2. Отсутствие публикации — факт, а не расхождение

**Выбор.** Ответы 404 и пустой список релизов дают отдельный результат «не опубликовано» с пояснением, что сравнивать не с чем.

**Почему.** Если считать это расхождением, то до первой публикации каждая генерация сопровождалась бы предупреждением о том, что устарела версия, которой никто не публиковал. Это шум, приучающий игнорировать предупреждения.

### 3. Сетевые обращения из стандартной библиотеки с таймаутом

**Выбор.** `urllib` с коротким таймаутом на источник, без кэша и без повторных попыток.

**Почему.** Пакет не имеет зависимостей, и добавление `requests` ради двух GET-запросов сломало бы это обещание. Кэш в каталоге пользователя означал бы состояние, которое нельзя увидеть и нельзя сбросить одной командой. Цена решения — до нескольких секунд на генерацию без сети; это приемлемо, потому что генерация идёт разово, а не в цикле.

### 4. Адрес репозитория и имя пакета берутся из метаданных пакета

**Выбор.** В `pyproject.toml` добавляется `[project.urls]`, а код читает имя пакета и адрес через метаданные установки.

**Почему.** Иначе в коде появятся константы с путём к репозиторию, которые разойдутся с `pyproject.toml` при первом же переименовании — ровно тот класс дефекта, который проверка пытается ловить.

### 5. Сверка с исходниками только при редактируемой установке

**Выбор.** Проверка выполняется, если рядом с кодом пакета найден каталог репозитория; иначе она пропускается без предупреждения.

**Почему.** В обычной копии исходников просто нет. Заявлять, что установить не удалось, вводило бы в заблуждение: копия полностью согласована сама с собой. Это различие и делает признак «установлено из исходников» наблюдаемым.

### 6. Только расхождение с шаблоном проекта блокирует работу

**Выбор.** Отказ с требованием явного флага даёт одно расхождение — версия шаблона проекта не совместима с установленным CLI. Остальные расхождения печатаются и не влияют на результат.

**Почему.** Несовместимый шаблон проекта даёт гарантированно нерабочий результат: файлы фичи окажутся не там, где их ждёт сборка, и пользователь потеряет работу. Отставание CLI от публикации даёт лишь устаревший, но рабочий проект. Флаг назван `--force`, а не чем-то двусмысленным, и влияет только на эту проверку, чтобы его смысл не расползался.

### 7. Тексты предупреждений перечисляют конкретные значения

**Выбор.** Каждое сообщение называет установленную версию, эталонную версию и, где применимо, команду обновления.

**Почему.** Сообщение вида «устаревшая версия» без чисел заставляет пользователя искать, где смотреть версию. Текущее сообщение об отказе по шаблону — пример такой бесполезной формулировки.

## Risks / Trade-offs

- [Проверка молчит там, где пользователь ждёт сигнала] → До первой публикации внешние эталоны не работают; это указано в сообщении явно, а сверка с исходниками при редактируемой установке покрывает случай разработчика. Средства, закрывающего устаревшую копию обычной установки, не существует — его заменяет редактируемая установка.
- [Задержка без сети] → Таймаут ограничен, повторы отсутствуют, а при недоступности печатается одна строка; генерация при этом продолжается.
- [Запросы к внешним сервисам из CLI] → Запросы выполняются только на чтение, без идентификатора пользователя, к заданному адресу репозитория и индексу пакетов.
- [Значение `--force` привыкнут трактовать как «делать что угодно»] → Флаг влияет только на проверку версии шаблона и описан именно так в справке и документации.
- [Ложное срабатывание сверки с исходниками] → Сравниваются версии, а не содержимое, и расхождение считается предупреждением, а не отказом.
