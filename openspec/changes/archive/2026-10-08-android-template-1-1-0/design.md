# Design

## Context

Основание для изменений — расхождение между двумя состояниями, изначально не связанными в коде (см. `proposal.md` — Why).

Текущий `templates/v1` (версия `1.0.0`) генерирует навигацию на Navigation Compose. Референсный проект, появляющийся при разработке новых приложений, построен на Navigation 3 и содержит модуль `:core:navigation`, типизированный контракт маршрутов и вкладки навигации, добавляемые feature-модулями в граф приложения. Код генератора о существовании Nav3 не знает вообще: поиск `nav3`, `core:navigation`, `AppRoute`, `NavKey`, `EntryProviderInstaller`, `serializable` по `src/` даёт ноль совпадений. При этом референсный проект помечен `template_version: "1.0.0"`, поэтому проверка совместимости в `metadata.py` его принимает, и `add-feature` начинает работать с проектом по правилам другой версии шаблона.

Механизм безопасности частично спасает ситуацию: якоря в `settings.gradle.kts`, `app/build.gradle.kts` и `App.kt` находятся, а проверки «уже зарегистрировано» отклоняют повторное добавление. Но проверки основаны на совпадении подстрок, а не на смысловой совместимости, поэтому расхождение не диагностируется — CLI сообщает «не поддерживается» лишь постфактум, без указания причины.

Смежные ограничения, влияющие на подход:

- Генератор не проверяет компилируемость результата. `--verify` существует только у `create`, а тесты подменяют запуск Gradle заглушкой, поэтому ничто в репозитории не доказывает, что сгенерированный проект собирается.
- Шаблон переиспользует проект в качестве API-модуля фичи, но без Android extension, поэтому у него нет `namespace`, а его контракт маршрута — строковая константа, непригодная для сохранения back stack.
- Соглашения в Gradle вынесены в `build-logic`, но часть решений в них зашита неудачно: `namespace` выводится склейкой пути проекта, из-за чего вложенный `:app:navigation` получает некорректное значение и требует ручного переопределения; `applicationId` захардкожен, хотя рядом читается свойство `basePackage`.
- `useJUnitPlatform()` настроен только для JVM-модулей. Android-модули подключают JUnit 5 библиотеками, но запускают их раннером JUnit 4, поэтому тесты в них молча не выполняются.

Целевой состав генерируемого проекта:

```
:app                  CompositionLocal провайдер, Koin start, NavDisplay
:app:navigation       START_ROUTE, TOP_LEVEL_ROUTES, сборка графа из вкладок
:core:navigation      контракт маршрутов, навигатор, состояние back stack
:core:designsystem    токены, типографика, палитра, тёмная тема
:common:presentation  базовый ViewModel
:common:testing       общие зависимости юнит-тестов
:feature:<slug>       data / domain / presentation / di / navigation
:feature:<slug>-api   сериализуемый маршрут как AppRoute
```

Поток навигации в целевом виде:

```
MainActivity
  rememberAppNavigationState(START_ROUTE, TOP_LEVEL_ROUTES)
  remember { listOf<EntryProviderInstaller> { userProfileSection() } }   <- стабильный список
  NavDisplay(entries = state.toEntries(provider), onBack = navigator::goBack)
        |
        +-- provider: entryProvider { entry<HomeRoute>; installers.forEach { it() } }
        |                    |
        |                    +-- userProfileSection(): EntryProviderScope<NavKey>
        |                          entry<UserProfile> { UserProfileScreen(...) }
        |
        +-- Navigator.navigate(route): верхнеуровневый -> смена активного back stack
                                    остальное     -> push в активный стек
```

## Goals / Non-Goals

**Goals:**

- Устранить расхождение между шаблоном и целевым дизайном так, чтобы сгенерированный проект совпадал с эталоном и воспроизводился из шаблона.
- Сделать скелет feature-модуля рабочим по всей цепочке, чтобы новый проект не наследовал мёртвые интерфейсы и незаполненные абстракции.
- Гарантировать выполнимость сгенерированных тестов, а не только их компилируемость.
- Перевести соглашения, которые сейчас требуют ручной доводки в каждом новом проекте, в convention-плагины.
- Сохранить отказ вместо молчаливой порчи для проектов других версий шаблона.

**Non-Goals:**

- Автоматическая правка Kotlin-исходников генератором: `add-feature` не подключает фичу к графу вместо разработчика.
- Рефакторинг и обновление уже созданных проектов, а также миграция `1.0.0` на новый шаблон.
- Настройка линтеров и статического анализа (`detekt`, `ktlint`, baseline профили, `packaging`-политики) — инфраструктура качества вне объёма этой версии.
- Изменение публичного CLI `create`, кроме добавления флага в `add-feature`.

## Decisions

### Навигация переносится в шаблон, а не откатывается в проектах

Целевым считается Nav3-дизайн референсного проекта, и он переносится в `templates/v1` как версия `1.1.0`.

Альтернатива: сохранить Navigation Compose в шаблоне и считать Nav3-проекты расхождением. Отклонена — тогда расхождение воспроизводится в каждом новом приложении, а `add-feature` продолжает генерировать непригодный контракт маршрута.

Альтернатива: сделать Nav3 отдельной опцией создания. Отклонена — две несовместимые схемы навигации в одном генераторе означают две ветки шаблонов и в `create`, и в `add-feature`, что противоположно цели унификации.

### Пустые `:common:domain` и `:common:data` удаляются

Слои `data` и `domain` остаются, но живут внутри каждого feature-модуля: это feature-first организация, а не layer-first.

Альтернатива: оставить модули как точки расширения для общих доменных типов. Отклонена — они пусты, `:common:domain` подключается из `app` и каждой фичи, то есть создаёт зависимость на пустоту, и провоцирует ошибочное предположение, что доменный код общий. Общие зависимости тестов в `:common:testing` при этом сохраняются и подключаются из convention-плагинов, поскольку пользу реально приносят.

### API-модуль фичи становится Android-модулем с сериализуемым маршрутом

Контракт маршрута — `@Serializable`-объект, реализующий `AppRoute`, в модуле с `android.library`, `android.serialization` и зависимостью `:core:navigation`.

Альтернатива: оставить `android.jvm.library`, добавив `@Serializable` без Android. Отклонена — модуль обязан видеть `AppRoute`, а тот живёт в Android-модуле `:core:navigation`; JVM-модуль не может от него зависеть.

Альтернатива: строковые route-константы с резолвом в графе. Отклонена — именно отказ от строковых маршрутов является смыслом перехода на Nav3.

### Вкладка навигации генерируется, подключение остаётся ручным

`add-feature` создаёт файл вкладки, который добавляет маршрут фичи в граф, и печатает готовый фрагмент кода. Исходники приложения не изменяются.

Альтернатива: `add-feature` сам дописывает вкладку в список установщиков в `MainActivity`. Отклонена — вкладка живёт в feature-модуле, а список установщиков находится в `:app`; это потребовало бы правки Kotlin-файла приложения по строковым якорям, что заметно повышает хрупкость плана и расширяет поверхность отката. Решение сохранено и в спецификации: сценарий «NavHost остаётся ответственностью приложения» остаётся в силе.

Существующий сценарий не переименовывается — его утверждение по-прежнему верно, меняется только то, что именно сообщает CLI.

### Фича генерируется с полной рабочей цепочкой

Вместо интерфейсов-заготовок создаются реализация источника данных, реализация репозитория, use case, регистрация репозитория и use case в DI и интенты во ViewModel, вызывающие use case. Состояние отражает загрузку, данные и ошибку.

Альтернатива: оставить интерфейсы и пометить незавершённость в коде. Отклонена — это и есть текущее состояние, и оно не учит ничему: каждая сгенерированная фича начинается с мёртвого доменного слоя.

Альтернатива: убрать доменный слой из скелета, оставив навигацию, UI и ViewModel. Отклонена — теряется демонстрация того, куда делить предметную логику и как связывать слои.

Источник данных намеренно остаётся заглушкой: это единственная часть цепочки, которую невозможно реализовать без предметной области нового приложения.

### `--verify` добавляется в `add-feature`

Проверка сборки переиспользует существующий механизм `create`; при ошибке файлы сохраняются, поведение совпадает с `create`.

Альтернатива: оставить проверку только в тестах репозитория. Отклонена — пользователь получает фичу и узнаёт о её неработоспособности только при первой сборке в IDE. Альтернатива «только в CI» потребовала бы отдельного интеграционного сценария в репозитории, что оставлено задачей тестов, а не флагом CLI.

Остаётся открытым, должен ли флаг быть включён по умолчанию — см. Open Questions.

### Тесты генерируются для ViewModel и репозитория

Оба теста используют подставные зависимости и не требуют Android-окружения; общий модуль `:common:testing` подключается как `testImplementation` из convention-плагинов.

Альтернатива: только тест ViewModel. Отклонена — тест репозитория показывает, что доменный слой проверяется независимо от платформы, что и требуется от feature-first организации.

### Тесты запускаются на JUnit Platform во всех Android-модулях

`useJUnitPlatform()` переносится из соглашения для JVM-модулей в соглашения `android.library` и `android.application`.

Без этого сгенерированные тесты компилировались бы и не выполнялись, то есть решение по их генерации не имело бы смысла. Это не отдельная опция, а условие корректности предыдущего решения.

Альтернатива: генерировать тесты на JUnit 4. Отклонена — в проекте уже используется JUnit 5 через `:common:testing`, и переход на JUnit 4 откатывал бы принятое решение.

### Дизайн-система наполняется токенами

`AppTheme` получает тёмную тему, типографику, палитру и набор extension-токенов; манифест получает тему, совместимую с Compose и edge-to-edge.

Альтернатива: оставить тонкой обёрткой над `MaterialTheme`, добавив только тёмную тему. Отклонена — без токенов дизайн-система не влияет ни на один экран: все обращаются к `MaterialTheme` напрямую, и модуль существует только для галочки.

### Версия шаблона поднимается, `1.0.0` перестаёт поддерживаться

`TEMPLATE_VERSION` становится `1.1.0`, CLI — `0.2.0`, карта поддерживаемых версий содержит только `1.1.0`.

Альтернатива: сохранить обе версии как поддерживаемые. Отклонена — проверка совместимости основана на совпадении подстрок и не проверяет смысловую пригодность проекта. Старый проект приняли бы и сгенерировали бы для него фичу по правилам нового шаблона. Отказ с явным сообщением о несовместимости — единственный вариант, который даёт пользователю диагностику.

Альтернатива: оставить `1.0.0`. Отклонена — тогда исправления соглашений и удаление `:common:domain` применятся к проектам, которые ждали старый состав модулей.

## Risks / Trade-offs

- **Удаление поддержки `1.0.0` ломает уже созданные проекты** → отказ с сообщением о несовместимости до записи файлов, без частичного применения. Обновление существующих проектов в объём не входит и оформляется отдельным изменением.
- **Изменение состава файлов `add-feature` ломает существующие тесты генерации** → тесты генерации обновляются в рамках этой же версии, ожидаемый список создаваемых файлов и применяемые плагины переписываются.
- **JUnit Platform в Android-модулях требует подтверждения на цепочке AGP и Gradle** → проверяется первым шагом реализации на временном проекте; при несовместимости генерация тестов переводится на JUnit 4, остальные решения сохраняются.
- **Правка соглашений затрагивает все модули сразу** → временный проект создаётся до применения правок к шаблону, чтобы не разворачивать изменения сразу на всех путях генерации.
- **`--verify` удлиняет цикл добавления фичи** → флаг остаётся opt-in; решение о поведении по умолчанию вынесено в Open Questions.
- **Правка строковых якорей в `feature.py` при добавлении новых зависимостей** → якоря добавляются рядом с существующими с сохранением проверки на единственное вхождение, отказ сохраняется при любом изменении формата файла.
- **Ручная регистрация destination сохраняет шаг, который легко пропустить** → CLI печатает готовый фрагмент кода, а не описание действий.

## Migration Plan

1. Подтвердить на временном проекте запуск JUnit 5 в Android-модулях; при несовместимости принять JUnit 4 для генерируемых тестов.
2. Обновить version catalog и соглашения: состав зависимостей, JUnit Platform, `namespace` вложенных модулей, `applicationId` из `basePackage`, `buildTypes`, явный `lifecycle-viewmodel`.
3. Добавить модуль `:core:navigation` с исправлениями против референсной реализации: стабильная идентичность списка вкладок, мемоизация производного списка записей, безопасная обработка back на стартовом маршруте.
4. Перевести `:app:navigation` и `MainActivity` на Navigation 3; снять ручное переопределение `namespace`.
5. Наполнить `:core:designsystem`, задать тему манифеста и edge-to-edge.
6. Переработать шаблоны `add-feature`: API-модуль, полная доменная цепочка, вкладка навигации, состояние, экран, тесты.
7. Поднять версии, обновить генератор, документацию и спецификацию.
8. Обновить тесты репозитория и добавить интеграционный сценарий `create` с проверкой сборки, добавление фичи с проверкой сборки.
9. Пересоздать эталонный проект из шаблона `1.1.0` и перепроверить его на соответствие обновлённой спецификации.

Откат: изменение целиком переносимо назад откатом Git — оно не добавляет внешних состояний в уже созданные проекты, поскольку новая версия шаблона отказывает, а не переписывает. Частичное откатываемое состояние — сгенерированный эталонный проект, который пересоздаётся целиком.

## Open Questions

- Должен ли `--verify` быть включён по умолчанию в `add-feature`, или остаться opt-in с включением в CI. Не влияет на спецификацию и на разбивку задач.
- Должен ли экран приложения, открываемый по умолчанию, оставаться в `:app:navigation` или выноситься в отдельный feature-модуль. Не влияет на спецификацию: модульный состав приложения уже зафиксирован.
