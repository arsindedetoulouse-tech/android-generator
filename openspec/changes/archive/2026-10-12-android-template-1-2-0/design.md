# Design

## Context

Шаблон `1.1.0` держит все слои фичи (`data`, `domain`, `presentation`) внутри feature-модуля. Эталонный проект `/home/yulia/dev/app-generated` довёл цепочку данных до офлайн-варианта: источник читает локальный кэш, загружает удалённые данные и сохраняет результат, репозиторий отдаёт кэш при отказе. Такой источник зависит от `DataStore<Preferences>`, а разбор заглушки — от `kotlinx.serialization-json`.

Из этого следуют ограничения на реализацию:

- `:core:datastore` сейчас опционален и появляется только с `--datastore`, а `kotlinx-serialization-json` попадает в version catalog только вместе с `--network`. Значит, проект без флагов не смог бы скомпилировать новую цепочку.
- Шаблонные файлы передаются в генератор как дерево с плейсхолдерами, а условия подстановки собираются в одном словаре `_optional_replacements`. Каждая библиотека version catalog сейчас либо присутствует всегда, либо появляется целиком по флагу.
- Ассеты Android-модулей сливаются в единый `assets` приложения на этапе сборки, поэтому код одного модуля читает ресурсы, поставляемые другим модулем.

Подробности мотивации — в `proposal.md`, наблюдаемое поведение — в `specs/android-project-generator/spec.md`.

## Goals / Non-Goals

**Goals:**
- Слои `domain` и `data` каждой фичи живут в общих модулях и переиспользуются между фичами.
- Цепочка данных офлайн-первая и одинакова для всех фич, включая начальную.
- Любой сгенерированный проект компилируется без дополнительных флагов.
- Ошибка в состоянии выражена типом, а не текстом исключения.

**Non-Goals:**
- Наполнение общих модулей доменным кодом, не относящимся к фичам: генерируются только типы фич.
- Автоматическая правка Kotlin-файлов уже созданных проектов.
- Локализация строковых ресурсов фич: источника переводов у генератора нет, поэтому строки фич остаются английскими.

## Decisions

### 1. `:core:datastore` переносится из опциональных модулей в постоянные

**Выбор.** Шаблон `optional/datastore` перемещается в `core/datastore` и рендерится при любом вызове `create`. Флаг `--datastore` удаляется из CLI вместе с ключом `options.datastore` в metadata.

**Почему.** Офлайн-кэш — часть контракта источника данных, а не отдельная возможность. Альтернатива «два варианта реализации источника в зависимости от флага» отклонена: интерфейс `DataSource` пришлось бы дублировать, и две реализации разошлись бы при правках, а проект без `--datastore` всё равно получил бы цепочку без кэша.

**Следствие для metadata.** `options` остаётся словарём без обязательной схемы, поэтому удаление ключа не ломает формат, но проекты `1.1.0` всё равно отклоняются по `template_version`.

### 2. `kotlinx-serialization-json` становится безусловной библиотекой каталога

**Выбор.** Версия `serialization` и библиотека `kotlinx-serialization-json` перестают зависеть от `--network`; в `_optional_replacements` под `--network` остаются только Ktor-записи.

**Почему.** Заглушка `<slug>_stub.json` разбирается через `kotlinx.serialization`, и этот разбор нужен в каждом проекте. Управлять зависимостью через несвязанный флаг означало бы, что проект без сети не собирается.

**Следствие для плейсхолдеров.** `__OPTIONAL_ANDROIDX_LIBRARIES__` и `__OPTIONAL_SERIALIZATION_VERSION__` больше не могут быть пустыми строками, иначе в TOML остаются пустые строки, которые ломают парсинг и проверяются тестом на пустые строки в списке модулей. Эти записи переносятся в постоянную часть `libs.versions.toml`, а плейсхолдер остаётся только у Ktor-записей.

### 3. Общие слои различают фичи пакетом, а не префиксом имени типа

**Выбор.** Модуль `:common:domain` получает исходники в `<package>/domain/<segment>/`, модуль `:common:data` — в `<package>/data/<segment>/`. Имена типов остаются `HomeModel`, `HomeRepository` без префикса слага.

**Почему.** Один набор типов на модуль проще поддерживать: генератор переиспользует шаблоны без вычисления префиксов. Плата — пересборка общего модуля при изменении любой фичи; для стартовых проектов это приемлемо, а при росте числа фич слои можно расщепить. Префикс в имени типа отклонён: он протекает в публичные сигнатуры и в Koin-регистрации.

### 4. Заглушка остаётся в feature-модуле, читается через `Context`

**Выбор.** `feature/<slug>/src/main/assets/<slug>_stub.json` поставляется feature-модулем, а `DataSourceImpl` в `:common:data` читает его через внедрённый `android.content.Context` по имени, производному от слага.

**Почему.** Ассеты всех модулей сливаются в приложение, поэтому общий модуль видит ассет, поставляемый фичей, без зависимости от feature-модуля — цикл зависимостей не возникает. Заглушка остаётся рядом с фичей, которой описывает данные. Альтернатива «перенести заглушку в `:common:data`» отклонена: она разорвала бы связь заглушки с фичей и заставила бы общий модуль выбирать, что читать.

### 5. Инфраструктурные биндинги в общих модулях, фичевые — в фиче

**Выбор.** `coreDataStoreModule` предоставляет `DataStore<Preferences>`. `di/<Фича>Module.kt` регистрирует `DataSource` (`DataSourceImpl(get(), androidContext())`), репозиторий, use case и ViewModel.

**Почему.** Общий модуль не знает о конкретных фичах, поэтому объявить в его Koin-модуле `HomeDataSourceImpl` невозможно без нарушения границы. Инфраструктура остаётся в инфраструктуре, а привязка типов к конкретной фиче — в её DI-модуле. `androidContext()` доступен в feature-модуле через соглашение `android.koin`, которое добавляет `koin-android`.

### 6. Юнит-тест репозитория переезжает вместе с реализацией

**Выбор.** `HomeRepositoryTest` создаётся в `common/data/src/test/kotlin/<package>/data/<segment>/`, а `HomeViewModelTest` остаётся в `feature/<slug>/src/test/`.

**Почему.** Тест проверяет реализацию репозитория, которая теперь находится в `:common:data`. Оставить тест в фиче значило бы завести тестовую зависимость feature-модуля на общий модуль ради одного класса. Тест ViewModel по-прежнему проверяет код feature-модуля и остаётся на месте.

### 7. Место ошибки в состоянии — закрытое перечисление

**Выбор.** Вместо `errorMessage: String?` состояние содержит `error: <Фича>Error?`, где перечисление содержит `Unknown` и `Network`. ViewModel отображает `IOException` в `Network`, всё остальное — в `Unknown`.

**Почему.** Строка ошибки исключения попадает в UI и в тесты, поэтому текст реализации становится контрактом. Тип ошибки отделяет классификацию от представления: экран решает, каким текстом показать ошибку, по значению перечисления. Расширение множества — добавление элемента перечисления, а не правка строк в нескольких местах.

### 8. Правки release-сборки и HTTP-клиента переносятся без изменений

**Выбор.** `isMinifyEnabled` и `isShrinkResources` включаются в release, AGP обновляется до `9.4.1`, клиент получает `expectSuccess = false` и явные таймауты.

**Почему.** Это наблюдаемые улучшения эталона, не требующие пересмотра. `expectSuccess = false` оставлен осознанно: универсальный модуль не решает за приложение, какой статус считать ошибкой, и передаёт ответ вызывающему коду.

## Risks / Trade-offs

- [Общий модуль пересобирается при изменении любой фичи] → Существующий общий модуль со слоями фич типичен для стартового этапа; при росте числа фич слои расщепляются по решению, уже зафиксированному в требованиях к слоям, без изменения поведения фич.
- [`kotlinx-serialization-json` больше не связан с `--network`] → Библиотека небольшая и уже присутствует в каталоге через `kotlinx-serialization-core`; изменение затрагивает только текст каталога.
- [`common:data` — Android-модуль, а тесты выполняются на JVM] → Тест репозитория работает через подставной `DataSource` и не касается Android API, поэтому `unitTests`-конфигурация не требуется; проверяется задачей `:common:data:test`.
- [Пустые строки в `libs.versions.toml` при переработке плейсхолдеров] → Убираются плейсхолдеры, которые могут стать пустыми; тест на отсутствие пустых строк в сгенерированных файлах остаётся.
- [`DataStore` пересекает границу модуля] → `androidx-datastore-preferences` объявляется как `api` в `:core:datastore`; проверяется компиляцией `:common:data`.
- [Удаление `--datastore` ломает скрипты генерации] → Ошибка argparse выдаётся до создания файлов и сообщает о неизвестном параметре; в README описан новый состав проекта.

## Migration Plan

Автоматической миграции проектов `1.1.0` нет, как и для `1.0.0`: состав файлов feature-модуля и общих слоёв изменился, а генератор не правит Kotlin-исходники существующих проектов. Порядок для пользователя: пересоздать проект новой версией CLI и перенести написанный вручную код фич в общие слои. Откат для ещё не выпущенной версии — возврат к предыдущему CLI: он поддерживает только `1.1.0`, поэтому проекты, созданные `0.3.0`, для него несовместимы.
