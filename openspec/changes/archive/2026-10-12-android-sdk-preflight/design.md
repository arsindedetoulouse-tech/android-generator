# Design

## Context

Проверка сборки сейчас безусловно зовёт Gradle и при отказе сообщает только код возврата. Между «проверка невозможна» и «сборка упала из-за кода» CLI не различает, поэтому пользователю остаётся читать вывод Gradle.

Три особенности окружения определяют решение:

- **Источников три, приоритет важен.** AGP читает `ANDROID_HOME`, `ANDROID_SDK_ROOT` и `sdk.dir` из `local.properties`. Значение может быть задано в любом из них, и задано неверным.
- **Наличие утилит в `PATH` не означает настроенный SDK.** Частично настроенная машина выглядит рабочей: `adb` доступен, переменной нет. Выводить путь из `PATH` без проверки признаков SDK нельзя.
- **Оболочку определить нельзя.** `$SHELL` в неинтерактивных сессиях не отражает оболочку пользователя, поэтому инструкция не может собираться под одну из них.

Дополнительно: `compileSdk` объявлен в двух конвенционных плагинах (`android.application`, `android.library`), а каталоги платформ в SDK называются неоднородно — `android-34`, `android-36.1`, `android-37.0`. Модульные версии платформ появились в SDK 36.1, поэтому сопоставление обязано понимать, что `android-37.0` удовлетворяет `compileSdk = 37`, а `android-36.1` — нет.

Мотивация — в `proposal.md`, наблюдаемое поведение — в `specs/android-project-generator/spec.md`.

## Goals / Non-Goals

**Goals:**
- Отказ проверки сборки называет причину и даёт способ её устранить.
- Gradle не запускается, когда сборка заведомо невозможна.
- Пользователь без Android Studio и без bash получает рабочую инструкцию.
- Никаких записей на диск без явного указания пользователя.

**Non-Goals:**
- Установка SDK, компонентов и лицензий — только инструкция со ссылкой.
- Проверка версии Gradle, JDK и наличия build-tools: эти ошибки Gradle формулирует понятно, и их разбор расширил бы область без заметной пользы.
- Поиск SDK по всей файловой системе: полная стоимость несоразмерна задаче.

## Decisions

### 1. Проверка предшествует запуску Gradle, а не разбирает его вывод

**Выбор.** Резолвер выполняется до `subprocess.run`; при провале Gradle не стартует.

**Почему.** Сборка без SDK падает за 30 секунд и печатает стектрейс. Проверка стоит миллисекунды и даёт адресное сообщение. Разбор вывода Gradle отклонён: он связывает генератор с формулировками чужого инструмента, которые меняются между версиями.

### 2. Приоритет источников повторяет порядок, который учитывает AGP

**Выбор.** `ANDROID_HOME` → `ANDROID_SDK_ROOT` → `sdk.dir` из `local.properties`. Первый найденный и пригодный побеждает.

**Почему.** Порядок совпадает с тем, что Gradle считает приоритетным, поэтому диагностика не может заявить «SDK не настроен» там, где сборка сработает. Первый источник, который задан, но непригоден, даёт отдельное сообщение о неверном значении, а не о ненастройке.

### 3. Каталог считается SDK только по признакам

**Выбор.** SDK — это каталог, содержащий `platforms` или `platform-tools`.

**Почему.** Пустой или посторонний каталог, заданный через переменную, иначе прошёл бы проверку существования и пропустил бы пользователя к тому же отказу Gradle. Эти два подкаталога присутствуют во всех установках, включая минимальные.

### 4. Запись в `local.properties` только по явному флагу `--sdk-dir`

**Выбор.** Автозаписи нет; `--sdk-dir PATH` записывает ровно указанный путь после проверки пригодности.

**Почему.** На рабочей машине обнаружено два валидных SDK, и они не равнозначны: у одного нет build-tools нужной версии. Молчаливый выбор привёл бы сборку к не тому и выглядел бы как «генератор сломался». Явный флаг делает решение пользователя видимым и в сообщении, и в самом проекте. Проверка пригодности выполняется до записи, поэтому флаг не может оставить в проекте нерабочее значение.

### 5. Кандидаты выводятся из положения `adb`, но не выбираются

**Выбор.** Путь строится как два уровня выше от найденной утилиты, затем добавляются типовые каталоги; всё это попадает только в текст инструкции.

**Почему.** Именно так восстанавливается частично настроенная машина, где утилиты доступны, а переменные не заданы. Выводить найденный путь в инструкцию полезно, выбирать его молча — нет (см. решение 4). Типовые каталоги добавляются потому, что машина может быть настроена корректно, но нестандартно.

### 6. Инструкция не зависит от оболочки

**Выбор.** Сообщение содержит блоки для zsh, bash, fish и Windows.

**Почему.** `$SHELL` в неинтерактивных сессиях показывает оболочку окружения процесса, а не пользователя. Строки для всех поддерживаемых оболочек стоят несколько строк текста и не могут оказаться неверными. Проверка применима к одинаковым файлам на всех системах, поэтому раздел один.

### 7. Требуемые уровни компиляции читаются из конвенционных плагинов

**Выбор.** Все значения `compileSdk` из `build-logic/src/main/kotlin/*.gradle.kts`, сопоставляемые с каталогами `platforms` по шаблону `android-<уровень>` с необязательным модульным суффиксом.

**Почему.** Объявлено два соглашения, и их значения могут разойтись. Жёстко зашитое `37` в генераторе разошлось бы с шаблоном при первой же правке шаблона. Модульный суффикс обязателен: без него `android-36.1` удовлетворил бы `compileSdk = 37`, а проверка по подстроке приняла бы и несуществующие уровни вида `android-370`.

## Risks / Trade-offs

- [Проверка пропускает сбой, который виден только внутри Gradle] → Сообщения остаются с инструкцией и указанием на `--stacktrace` для нестандартных причин; охват сознательно ограничен расположением SDK и платформами, где ошибка иначе нечитаема.
- [`--sdk-dir` создаёт машинно-зависимый файл в проекте] → Файл уже исключён `.gitignore` шаблона и не попадает в коммит; он создаётся только по явному флагу и никогда не перезаписывает файл, созданный неявно.
- [Проверка платформ даёт ложное требование при составной версии SDK] → Шаблон допускает модульный суффикс ровно того вида, который встречается в установках (`android-37.0`, `android-36.1`); при появлении иной схемы записи проверка откажет с перечнем установленных каталогов, а не промолчит.
- [Кандидаты расходятся с реальным SDK после переноса машины] → Кандидаты попадают только в текст инструкции; запись в проект происходит исключительно по указанному пользователем пути.
- [Предупреждение без `--verify` шумит на машинах, где SDK настроен] → Предупреждение печатается только когда SDK не настроен, а не при каждой генерации.
