# Design

## Context

Проект — Python-пакет `android-skeleton` (версия 0.3.0 в `pyproject.toml`, версия Android-шаблона 1.2.0), распространяемый как CLI. Публикационная инфраструктура в нём отсутствует полностью: нет `LICENSE`, нет CI, нет тегов и релизов, пакет не загружен на PyPI. Имя репозитория на GitHub (`android-generator`) расходится с именем пакета (`android-skeleton`); код читает адрес репозитория из метаданных установленного пакета (`pyproject.toml` → `[project.urls]`), поэтому переименование репозитория не потребовало бы правок кода — но менять имя в момент первого релиза признано избыточным.

Ключевое внешнее ограничение: публикуемое имя `android-skeleton` на PyPI свободно, версии 0.3.0 там не существует. Аккаунты: PyPI и GitHub — один и тот же владелец, `arsindedetoulouse-tech`.

## Goals / Non-Goals

**Goals:**
- Получить рабочий одноразовый релизный цикл, который повторяется на следующих версиях без переписывания.
- Не хранить в репозитории секрет, имеющий право загружать пакет.
- Сделать проверку версий CLI (`version_check.py`) успешной у пользователя опубликованной версии.

**Non-Goals:**
- Переименование репозитория и пакета.
- Полировка поведения генератора; спецификация `android-project-generator` не затрагивается.
- Подбор и настройка линтеров (ruff, mypy) — их в проекте нет, и вводить их вместе с релизом значит менять требования к разработке, а не к дистрибуции.

## Decisions

**Лицензия — MIT.** Формат текста, который GitHub узнаёт без настройки, поэтому лицензия отобразится на странице репозитория сама. Альтернативы (Apache-2.0) отклонены: у проекта нет патентной защиты, ради которой берут Apache, а длинный текст ничего не добавляет для одностороннего CLI-инструмента.

**Файлы лицензии в артефактах не перечисляются вручную.** `pyproject.toml` уже требует `setuptools>=77`, который включает файлы лицензии в sdist и wheel по умолчанию. Явный `license-files` не нужен: добавление ключа означало бы ещё одно место, которое придётся синхронизировать с корнем репозитория.

**README делится на два файла, а не переводится в один.** Английский `README.md` — то, что читают по ссылке с PyPI и из поиска GitHub; русский текст сохраняется как `README.ru.md`. Один файл с двумя языками заставил бы читателя выбирать между блоками; удаление русского варианта отняло бы у автора рабочий язык. Links взаимные в шапке обоих файлов.

**Расхождение имён не исправляется, а объясняется.** Строка в README рядом с командой установки: пакет называется `android-skeleton`, репозиторий — `android-generator`. Переименование отложено: оно меняет URL для всех существующих ссылок и `[project.urls]`, а выигрыш косметический.

**CI и публикация разнесены по разным workflow-файлам.** `ci.yml` запускается на каждый push и pull request: матрица Python 3.11/3.13/3.14, затем `python -m build` и `twine check dist/*`. `publish.yml` запускается только на теге `v*` и выполняет `twine upload --trusted-publishing always`. Один файл с условием `if:` на тике выглядел бы компактнее, но смешивал бы два разных права: у ветки есть право запускать сборку, у тега — публиковать.

**Trusted Publishing, а не API-токен.** При PyPI Trusted Publishing токен выдаётся OIDC-обменом от GitHub Actions конкретному workflow и настраивается через `environment: pypi`. Сравнение с API-токеном в `~/.pypirc` не случайно: токен в репозитории не нужен, но он живёт на машине разработчика и переживает ротацию репозитория. Условие — одноразово завести publisher на pypi.org, указав владельца `arsindedetoulouse-tech`, имя репозитория `android-generator` и имя workflow-файла `publish.yml`; без этого шага публикация падает на стороне PyPI. Окружение `pypi` дополнительно требует ручного подтверждения в настройках репозитория — это осознанно: загрузку пакета нельзя запустить чужим PR.

**Версия релиза не сбрасывается.** Тег `v0.3.0` повторяет `pyproject.toml`, хотя это первый публичный релиз: нумерация ведётся по внутренней разработке, и обнуление её здесь означало бы расхождение версий в `.android-skeleton.json` уже созданных проектов. Тег с префиксом `v` обязателен — иначе публикация не срабатывает.

**Проверка метаданных идёт до загрузки, а не после.** `twine check` выполняется в шаге с `needs`, чтобы плохое описание не публиковалось и не требовало отзыва релиза.

## Risks / Trade-offs

- [Trusted Publishing не настроен на стороне PyPI] → workflow падает на шаге публикации без загрузки; в задачах публикация идёт последним шагом, после проверки артефактов, а регистрация publisher перечислена отдельной задачей с ручным подтверждением.
- [Тег `v0.3.0` отправлен до готовности workflow] → тег ставится после зелёного прогона CI; публикующий workflow проверяет, что версия в `pyproject.toml` совпадает с именем тега, и отказывается при расхождении.
- [В README появляется английский текст, который устареет раньше русского] → оба файла описывают одну и ту же версию CLI; в русском файле остаётся строка с тем же номером версии, и задачи публикации следующей версии включают обновление обоих.
- [Пакет уйдёт на PyPI с ошибкой, которую не поймал `twine check`] → после загрузки выполняется проверка в чистом venv: установка из индекса и `create` в пустом каталоге.
- [Отсутствие API для GitHub в этой среде] → описание репозитория и топики выставляются либо через `curl` с токеном, либо вручную в веб-интерфейсе; на результат публикации это не влияет.

## Migration Plan

Порядок обратим до шага публикации: файлы документации, лицензия и workflow добавляются в репозиторий обычным коммитом. Если что-то в этом наборе окажется лишним, достаточно удалить файлы — на код генератора они не влияют. Откатить уже опубликованную версию на PyPI нельзя, поэтому публикация 0.3.0 — последний шаг и проводится только после зелёного CI.
